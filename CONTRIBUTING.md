# Contributing to tightship

English · [Português](CONTRIBUTING.pt-BR.md)

Bug reports, ideas, and pull requests are welcome. This page covers how a change moves from an issue to a
merge, how to set up the repository, and the gates a pull request must pass.

Everyone taking part follows the [Code of Conduct](CODE_OF_CONDUCT.md). Report a vulnerability as
[SECURITY.md](SECURITY.md) describes, never in a public issue.

## Start with an issue

Every change starts with an issue, including small fixes. Open a bug report or a feature request from the
[issue forms](https://github.com/ATNexusLab/tightship/issues/new/choose), and wait for the maintainer to
confirm the scope before you write code. A pull request without an issue is closed with a request to open
one.

A change to what the product must do is a change to the [requirements](docs/requirements/README.md). It
goes through a `requirement-change` issue, and the maintainer decides it before any code changes.

## Set up

You need:

- `rustup`. The toolchain is pinned in `rust-toolchain.toml`, and `rustup` installs it on the first `cargo`
  call.
- gitleaks 8.30.1 on the `PATH`, for `cargo xtask scan` and the tests.
- Node.js, for `npx markdownlint-cli2`.
- `uv`, for the docs site through `uvx`.
- Git for Windows on Windows. Run every command in Git Bash.

Then create `.identity-terms` at the root of your clone. git ignores it. Put one line per name, email
address, user name, and handle of yours. The build fails if any of them appears in what it ships, so your
identity never leaks into the plugin. The build also needs the file to exist.

## Make the change

1. Fork the repository and branch from `develop`: `<type>/<issue>-<slug>`, for example
   `fix/52-hook-exit-code`.
2. Keep each piece in its place:
   - `content/` holds the one copy of every piece and names no harness, path, or tool of one. A reference
     to another piece, a harness capability, or an option is a `{{<kind>:<name>}}` token.
   - `harnesses/<harness>/` is the only place a harness is named.
   - `dist/` is generated by `cargo xtask build`. Never edit or commit it.
3. Write the code in Rust and the docs in English. Prose in `docs/` wraps at about 105 columns. When you
   change `README.md`, this file, `SECURITY.md`, `CODE_OF_CONDUCT.md`, or a page of `docs/install/`,
   update its `.pt-BR.md` translation in the same commit. If you don't read Portuguese, say so in the pull
   request and the maintainer updates it.
4. Add a test when the change alters behavior someone can observe, such as logic, a rule, or a bugfix, and
   write it before the code. Changes to style, copy, config, or docs need none.
5. Update the docs the change affects in the same pull request.

## Run the gates

Run them cheapest first. Each must exit 0 with no warnings.

| Gate | Command |
| --- | --- |
| Markdown lint | `npx markdownlint-cli2@0.23.3` |
| Rust lint | `cargo clippy --workspace --all-targets -- -D warnings` |
| Secrets and identity scan | `cargo xtask scan` |
| Type check | `cargo check --workspace --all-targets` |
| Formatting | `cargo fmt --all --check` |
| Docs build | `uvx zensical==0.0.70 build` |
| Plugin build | `cargo xtask build` |
| Tests | `cargo test --workspace` |

To try your build in a session, run `claude --plugin-dir dist/claude-code`.

## Open the pull request

- Commits follow [Conventional Commits](https://www.conventionalcommits.org/): one imperative line in
  English, such as `fix: keep the session alive when the vault is missing`.
- The pull request targets `develop` and says `Closes #<issue>` in its description.
- Fill in the template: what changed, why, and how you checked it.

On a pull request from a fork, the Rust workflow fails at the plugin build: a fork gets no repository
secrets, so the runner has no `.identity-terms`. Your local gates are the check that counts until the
maintainer pushes your branch to this repository, which runs CI on macOS, Linux, and Windows.

The maintainer reviews every pull request and merges it into `develop`. Releases go from `develop` to
`main`.
